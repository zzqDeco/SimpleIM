# SimpleIM engineering instructions

- Keep the central server (`apps/server`) strictly minimal and zero-knowledge for room traffic. It handles only open self-service account registration/authentication, short-lived `Ed25519` `PeerIdentityCert` issuance, and ephemeral in-memory WebSocket signaling relay. Once WebRTC `RTCDataChannel`s open, all chat messages, catch-up sync, and file chunks flow peer-to-peer without touching the server.
- Full-stack TypeScript on Bun (`Bun.serve()`, `bun:sqlite`, `Bun.password`); React 19 + Vite + native WebRTC + Web Worker OPFS in `apps/web`; pure-TypeScript `werift` WebRTC + native filesystem chunk storage in `apps/cli` so `bun build --compile` produces standalone binaries with zero C++ `node-gyp` addons.
- Read `docs/contracts/signaling-v1.md` and `docs/contracts/p2p-v1.md` before changing wire protocols, cryptographic derivations, or module APIs. Coordinate contract changes across `packages/contracts`, `apps/server`, `apps/web`, and `apps/cli` in the same pull request.
- `apps/server` owns a single WAL-mode `bun:sqlite` database containing exclusively `schema_migrations`, `users`, and `sessions` (`token_sha256` hashes only, never plaintext session tokens). Never add room, group-membership, chat-history, or file-metadata tables to the server database; signaling room membership lives solely in process memory and evaporates on disconnect.
- Passphrase-to-room derivation executes exclusively on the client: normalize passphrase with Unicode NFC, derive a 32-byte seed via `Argon2id` (`m = 65536 KiB`, `t = 3`, `p = 1`), and expand orthogonal subkeys (`roomId`, `signalingKey`, `roomAuthKey`, `roomAppKey`) via domain-separated `HKDF-SHA256`. Never send plaintext passphrases, `masterSeed`, or derived encryption keys to the server, URL query strings, or `localStorage`.
- WebSocket signaling payloads (`sdp-offer`, `sdp-answer`, `ice-candidate`, `ice-end`) must be end-to-end encrypted with `signalingKey` (`XChaCha20-Poly1305`, binding `roomId`, `fromPeerId`, and `toPeerId` as AAD). The signaling server never broadcasts plaintext usernames on `room.joined` / `room.peer_joined`; participant identities are disclosed only inside the encrypted post-DTLS handshake.
- Every WebRTC peer pair deterministically initiates two negotiated channels (`id: 0` `"control-chat"` ordered, `id: 1` `"file-swarm"` unordered binary) from the lexicographically smaller `peerId` (`localPeerId < remotePeerId`) and starts in `UNVERIFIED` quarantine. Reject all chat and file frames until `HELLO_AUTH` verifies: (1) valid `serverSignPubKey` signature and expiry on `PeerIdentityCert`, (2) `roomAuthKey` HMAC proof, and (3) `peerSignPrivKey` signature bound to both peers' observed DTLS certificate SHA-256 fingerprints.
- Chat messages and `FileManifest` announcements carry the author's `PeerIdentityCert` and `Ed25519` signature so online catch-up relays from verified peers remain tamper-evident without server involvement.
- Swarm file transfers split files into `64 KiB` (`65,536 B`) chunks framed in big-endian binary on `"file-swarm"` (never Base64 JSON), enforce `SHA-256` verification per chunk before disk/OPFS commit, bound `dc.bufferedAmount` (`<= 1 MiB` high-water mark with `bufferedamountlow` resumption), and isolate `apps/web` large-file storage inside Web Worker OPFS (`FileSystemSyncAccessHandle`) rather than in-memory `ArrayBuffer` arrays.
- `apps/cli` must never accept a plaintext `--passphrase <secret>` CLI flag (visible in process tables); prompt with hidden echo or read via `--passphrase-stdin`. Sanitize incoming `FileManifest.fileName` values with `basename` and reject path traversal or silent overwrites.
- The only persistent deployed environment is `production`. `main` is the only ongoing development branch; `release/vx.x.x` branches and tags are permanent immutable archives. Never delete or rewrite a published release branch/tag; fixes land on `main` and cut a new version.
- Never commit `.env` files, private signing keys, SQLite databases, `.runtime/` directories, or temporary `.simpleim.part` artifacts.
- Structured JSON boundary logs must record integer millisecond durations, correlation IDs, truncated 8-hex `roomId` prefixes, and safe error codes—never passwords, session tokens, passphrases, derived keys, SDP/ICE bodies, chat message text, file names, or file bytes.
- Meaningful tests must cover `Argon2id`/`HKDF` vectors, `HELLO_AUTH` MITM/tamper rejection, server SQLite zero-room-persistence guarantees, Web ↔ CLI WebRTC interoperability, center-server shutdown survival on active P2P channels, and multi-peer Swarm chunk verification/poisoning rejection. Build/typecheck alone does not constitute acceptance.
